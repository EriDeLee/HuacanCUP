- 影响：PLAN §0、§1.2、§1.5、§2、§3、§4、§5.3、§5.4、§6、§7（G2）、§8、§11、§12、§13、§14、§15、§16；
  以后要改的代码（这次没改）：`eda_agent/orchestrator/rundir.py`、`schemas/trace.schema.json`（加 branch id）、网页回放代码

## 背景

同一份需求，电路本来就有多种做法，成本、精度、面积、焊接难度各不相同。以 4 串锂电池短路与过流保护板为例，至少有：

- 比较器 + MOSFET 分立方案；
- 专用多串电池保护芯片；
- 电子保险丝 / 热插拔控制芯片；
- 保险丝 + PTC 被动保护。

PLAN 原来的 S2 是「给出 2~3 种拓扑，选定一个」，选哪个靠模型判断。
改成几种都做出来，由确定性的 Gate 和程序算出的指标来选，更符合硬原则「通过与否只能来自确定性程序」。

## 决定（用户）

### 分叉点

在 S2 方案阶段之后分叉。S0 需求、S1 确认只跑一次，spec 在分叉前冻结，所有路共用同一套验收标准，结果才能比较。

### 分支结构：3 × 3 = 9 路

- 方案智能体给出 3 种明显不同的拓扑。
- 每种拓扑下，选型智能体按 3 种不同策略各出一路，合计 9 路：
  - 优先用户库存；
  - 优先 JLC 基础件；
  - 优先最小面积。
- 拓扑数和策略数做成配置项，默认 3 × 3。

### 每路独立运行

- 每路独立走 S3 选型 → S4 原理图 → G1 → S5 测试台 → G2 → S6 诊断回退 → S7 版图 → G3。
- 回退次数上限按路单独计算。某路超出上限就终止，保留它的最好状态和未通过项。
- 「独立」指每路有自己的状态、回退计数和运行目录，不等于路与路之间不说话，见下面「路与路之间的交流」。

### 防止各路趋同

- 每路的提示里带明确的差异约束，例如「这一路必须使用专用保护芯片」。
- 分叉后由程序计算每路的拓扑和 BOM 指纹，重复的路合并掉，不经模型判断。

### 路与路之间的交流（用户 2026-11-08 补充，选了「轻量版」）

用户说：Agent Swarm 里的 agent 之间也要有交流，是一个集群，不是各跑各的。我理解「集群」是一群 agent 协同工作，不是多台机器。

先做两种（用户 2026-11-08 选定）：

- **共享记事板**：各路把查到的事实写在一块公共板上，别的路能读。例如某个比较器缺货、某份数据手册里的坑、某个仿真量到的数值。
  只共享事实，不共享整份设计。
- **失败教训广播**：某路没过 G1、G2 或 G3 时，发一条「为什么没过」给所有路。

约束：

- 判定仍只来自 Gate，交流只影响智能体提什么方案。
- 每条消息是结构化记录，记进 `trace.jsonl`，带发送路的 branch id；网页时间线能看到。
- 各路仍保持不同：差异约束和指纹去重照留。

用户看过但这次没选、以后可以往上加的：互相评审、协调员智能体、做的途中借用对方的子电路、选优时拼混合路。
「自由对话」没有固定格式，最难复现和排查，和「所有记录进 trace、能回放」冲突最大，没放进任何一套。
轻量版的工作量我估计 2–3 天（估计，未验证），在 M3 做并行时一起做。

### 汇合与选优

- 只在 G1、G2、G3 全部通过的路之间比较。
- 排名由确定性程序计算，依据：每条验收标准的仿真余量、板面积、BOM 成本、库存件占比。权重写在配置里，运行前固定。
- 总审智能体（ReviewAgent）只做两件事：为每一条被淘汰的路写淘汰理由；照旧写「风险与未验证项」。
  它**不能改变排名，也不能宣布通过**。PLAN §6 总审一行已同步改写。
- 一路都没有全部通过时，按通过的 Gate 数量和失败项排出「当前最好」交给用户，不得隐瞒未通过项。

### 人工节点

仍然只有 S1、S9 两个必经人工节点。S9 的审批卡片展示胜出方案，附其余各路的一行摘要和淘汰理由。采购只针对胜出方案。
用户可以在 S9 改选另一路，见「审查后的决定」第 2 条。

### 费用

用户 2026-11-08 补充：费用先不管。

- 共享阶段（S0–S2）只跑一次。这是结构上的事（分叉在 S2 之后），照旧。
- 整次运行的费用上限按全部分支合计：保留。它只是把各路的花销加起来（花销本来就记在 trace 里），和原有的「超限暂停并询问」一起用。
- 原来定的另外两条先不做，实现并行时不为它们写代码，等看到真实花销再定：
  - 分支阶段在过 G1 之前用便宜的模型，过了 G1 的路再用强模型；
  - 超出预算时，按当前排名从末位开始终止分支。

### 运行目录与记录

- 运行目录改为 `runs/<run_id>/branches/<k>/iterations/NN/`。
- `trace.jsonl` 每条记录加 branch id。
- 网页时间线要能分路显示。

### 评测

PLAN §13 加一组对比：单路串行 vs 九路并行，比较全部 Gate 通过率、最终指标、费用、耗时。
再加一组等预算对比：串行流程用同样的总预算，多次重试。

### 对外说法

PLAN 里写「其他整板生成工具是单条流水线」，不写「竞品都是串行」。
原因：Quilter 本身就会同时生成多个布局布线候选，只是它只做布线（竞品表见 PLAN §1.5）。
我们的不同在于「多种方案并行做完，由程序检查结果选优」；不写「首创」「唯一」。

## 我补充的几处（用户没明说，按下面的理解写进了 PLAN；不对就改）

1. **汇合步骤放在 S8（采购）之前**，编号 S7b，不是「S10 之前」。采购只针对胜出方案，S9 要展示胜出方案，
   所以必须在这两步之前选出来。S8–S11 的编号不动。
2. **S6 诊断认为拓扑本身不行时，多路并行的这一路终止，不回 S2。** 别的拓扑已经在别的路里跑；
   回到 S2 会让几路收敛到同一个拓扑。路数配成 1 × 1（单路）时，方案智能体只给 1 种拓扑，S6 仍可回 S2。
   （2026-11-08 审查后改：判断条件从「是不是单路」改成「拓扑是不是只有 1 种」，见「审查后的决定」第 1 条。）
3. **指纹分两次算。** 拓扑指纹在分叉时算；BOM 指纹要等 S3 选型完成才有，算出来相同的两路合并成一路继续。
4. **每路的 `sim/`、`kicad/` 放在 `branches/<k>/` 下**，因为每路各自仿真、各自出板。
   单路运行也用 `branches/0/`，目录布局不分两套。另加 `ranking.json`（汇合结果）放在运行目录根部。
   （2026-11-08 审查后补：S10 打包时再复制一份进 `final/`，见「审查后的决定」第 3 条。）
5. **G2 报告对通过的验收标准也记实测值、阈值和余量**，排名要用（PLAN §5.3、§7）。
6. **超预算的衔接**（费用相关，用户说先不管，暂不实现）：原来写「超限暂停并询问」，我写成「多路并行时先按当前排名从末位终止路；
   只剩一路仍超限才暂停询问」。
7. **选型策略只在底线之内排序**：额定值（含降额）和封装可装配（spec 约束）三种策略都必须满足，策略不放宽它们（PLAN §8）。
8. **分支阶段的档位规则单路也适用**（费用相关，用户说先不管，暂不实现）：选型、原理图、诊断、版图四个角色不再按 PLAN §6 表里的档位，
   而是按这一路的进度（过 G1 之前便宜档，过了 G1 强档）。这样串行和并行的评测用同一套规则，可以比。

## 审查后的决定（用户 2026-11-08）

审查这份 ADR 时发现三处没写清楚或互相对不上，用户逐条选定：

1. **拓扑只有 1 种时，拓扑不行就回 S2。** 原来的条件是「单路才回 S2」。可是方案智能体可以只想出 1 种拓扑
   （「有几种给几种」），这时多路运行的几路用的是同一种拓扑，拓扑不行会一起被终止，没有别的拓扑可以接着跑，
   比单路更早放弃。现在：拓扑只有 1 种（不论几路），用它的各路一起回 S2 换拓扑、重新分叉；
   拓扑有 2 种及以上时照旧只终止这一路。3 种拓扑全都不行时仍然不回 S2，按「当前最好」交给用户。
2. **S9 可以改选另一路。**
   - 只能选 G1、G2、G3 全部通过的路。
   - 改选后回 S8 为它生成采购申请，再推一次审批卡片；采购申请总是用户看过才算批准。
   - `ranking.json` 里程序算的名次不变，另记一笔用户选了哪一路，评测时还能统计程序选优和用户的选择是否一致。
   - `final/` 放用户最终选的那一路。
3. **`ranking.json`、`trace.jsonl` 两处都放。** 原件在运行目录根部；S10 打包时各复制一份进 `final/`，
   用户只下载 `final/` 也能看到方案对比和全过程记录。复制的是打包那一刻的内容，之后（例如 S11）追加的记录只在原件里。

## 还没定的（列在 PLAN §16）

- 余量怎么归一、四项指标怎么合成一个分数。
- 板面积怎么算。现在 `board.size_mm` 是输入（设计里写定的板尺寸），不是结果；按面积排名需要每路有自己的板尺寸
  （版图智能体缩板，或取摆放后元件的外包框）。
- 路与路之间的交流（轻量版）：消息的字段、哪些事实该写进记事板、各路读多少（进提示时怎么取舍，见 PLAN §3.1）、
  和「防止各路趋同」怎么共存；评测要不要加「有交流 / 无交流」一组；以后要不要加评审、协调员、借用子电路、拼混合路。
- 并行专门的费用控制（便宜到强的档位、超预算按排名终止）：先不管，以后再定。超预算时「当前排名」怎么算
  （运行中途还没有全部 Gate 的结果）、什么时候触发、一次终止几路，到时一起定。
- spec 里已有的 `constraints.prefer_inventory`、`budget_cny` 和新的选型策略、排名怎么衔接
  （`prefer_inventory` 与「优先用户库存」这一路重叠；`budget_cny` 现在没有任何 Gate 检查它）。
- 方案智能体想不出 3 种明显不同的拓扑时怎么办（现在的想法是有几种给几种，不凑数；指纹去重本来也会合并重复的）。
- 差异约束的写法、指纹算法。
- 评委网页的实时模式默认跑几路、费用上限多少（九路并行放大费用）。

## 实现顺序

先跑通单路端到端，再做并行；不要让并行挡住单路的薄切片。

里程碑位置（用户 2026-11-08 选定，PLAN §12）：

| 里程碑 | 做什么 |
|---|---|
| M2 | G2 报告记余量。成本很小，先做免得返工 |
| M3 | 运行目录和 trace 从第一天起按 `branches/<k>/` 和 branch id 写，单路只有 `branches/0/`。单路（1 × 1）跑通并验收后，再做分叉、指纹去重、路间交流、汇合选优（`orchestrator/swarm.py`）。并行做不完就挪到 M4 之后、M5 之前补完，不占 M4 的时间 |
| M4 | 目录和库存接入后，三种选型策略换成真实数据（之前用手写的小零件表） |
| M5 | 网页时间线分路显示，S9 卡片展示各路、可以改选 |
| M7 | 评测加上串行 / 并行 / 等预算三组对比 |

理由：

1. 编排器的状态、预算、运行目录、trace 都要认得「路」。一开始就按路写，比单路做完再改便宜；
   但分叉和汇合本身要等单路跑通，所以放在 M3 的第二步。
2. 三种选型策略要有目录和库存数据（M4）才有区别，所以引擎在 M3，真实数据在 M4。
3. M5 的网页时间线、M7 的评测都要用多路的 trace，引擎要在 M5 开工前做完。
4. 排名是确定性程序，用手写的 GateReport 就能单测，不用等模型。

## 后果

- `rundir.py` 和 `trace.schema.json` 是按旧版 PLAN §5.4 写的（ADR-0013），没有「路」这一层，M3 开头要改；
  回放代码也要按 branch id 分路。
- 分支阶段的模型调用随路数增加。现在只靠「共享阶段只跑一次」和「总额度按合计」；
  「过 G1 才换强模型」「从末位终止」先不做（用户 2026-11-08：费用先不管）。
- 路与路之间的交流要新增一类事件记进 trace，`trace.schema.json` 和回放代码要跟着改（消息格式定了以后）。
- 单路仍是整个系统的最小可用形态（路数配成 1 × 1）。
